### How it works

1. **Login once** — first run asks for phone number + OTP, saves session to disk (no re-auth needed after)
2. **Listen** — attaches to a target group, reads every new message
3. **Match** — for each message, checks:
   - Does it contain any configured **keyword**?
   - Is the sender in the **target users** list?
4. **Randomize** — even on a match, it sometimes ignores the message (30-50% chance to skip) — this breaks predictable patterns
5. **Act** — performs one or more:
   - React with a random emoji (from a configurable pool)
   - Reply with a random message (from a template pool)
   - Click a random inline button if present
6. **Throttle** — enforces max actions/hour, with randomized delays between actions (1-15 seconds)

### Anti-detection layers

| Layer | Technique |
|-------|-----------|
| Protocol | Uses MTProto (identical to official clients), **not** browser DOM automation |
| Device info | Spoofs a real Samsung/iPhone device model, Android/iOS version, and official app build |
| Timing | Weighted random delays, not uniform. Occasionally "idles" for minutes. |
| Selectivity | Randomly skips 30-50% of matches; never reacts to 100% of anything |
| Volume | Sliding window rate cap (e.g., max 60 actions/hour configurable) |
| Patterns | Varies emoji choice, reply text, and delay between action types |

Yeah, you can. The concept is called **"Computer Use"** or **AI Agent with screen control**. Several big players are already doing it:

| Tool | Approach |
|------|----------|
| **Claude Computer Use** (Anthropic) | Screenshots → Claude Vision → mouse/keyboard actions |
| **OpenAI Operator** | Same idea, GPT-4o as the brain |
| **Browser-use / Stagehand** | Browser-only subset, but same principle |
| **OS-Copilot / UFO** | Open-source attempts at full desktop agents |

### How it works at its core

```
┌─────────────┐    screenshot    ┌──────────────┐    coordinates/clicks    ┌──────────────┐
│  Screen      │ ──────────────> │  AI (GPT-4o, │ ─────────────────────>  │  OS Input    │
│  Capture     │                 │  Claude)      │                        │  Emulation   │
└─────────────┘                  └──────────────┘                        └──────────────┘
      ^                                                                          │
      │                                                                          │
      └────────────────── screen changes ────────────────────────────────────────┘
```

1. **Capture the screen** → send to a vision-capable LLM
2. **LLM sees the screen**, understands what's there, decides what to click/type
3. **Execute the action** via OS-level input emulation (mouse click, keyboard)
4. **Capture again** → loop

### What you'd need to build it

| Layer | Node.js libraries |
|-------|-------------------|
| Screen capture | `screenshot-desktop`, `sharp`, platform-specific |
| AI vision | OpenAI API (GPT-4o), Anthropic API (Claude), or local VLM |
| Input emulation | `nut-js`, `robotjs` (mouse move, click, type) |
| Remote access | **WebRTC** (peer-to-peer streaming) or **WebSocket + JPEG stream** |
| Security/auth | TOTP, signed tokens, whitelist |

### The hard parts (that AnyDesk already solved)

1. **Latency** — LLM calls take 1-5 seconds. Not real-time like a human remote desktop session.
2. **Cost** — every screenshot is an API call. A 1-hour session could be hundreds of screenshots × ~$0.01-0.03 each.
3. **Reliability** — AI sometimes misclicks, misunderstands UI, or gets stuck in loops.
4. **Security** — giving an AI full mouse/keyboard control is dangerous. You need a sandbox or VNC-style confirmation.
5. **Streaming** — real-time screen streaming at 15-30fps to a remote viewer is a separate hard problem from the AI control loop.

### Why GramJS is hard to detect

| Factor | Why it helps |

| Risk | How serious? | Mitigation |
|------|:---:|---|
| **Spam-like frequency** (50 reactions/minute) | **High** | Rate limit to ~60 actions/hour max |
| **Predictable timing** (exactly every 3 seconds) | **Medium** | Weighted random delays (1-15s) |
| **0% skip rate** (reacts to every single target message) | **Medium** | Randomly skip 30-50% of matches |
| **Single-emoji pattern** (always reacts with 🔥) | **Low** | Rotate from a pool of 5+ emojis |
| **Joining 50+ groups rapidly** | **High** | Don't mass-join groups |
| **Running same account on phone + bot simultaneously** | **Very low** | Telegram natively supports multi-session. Normal users do this (phone + tablet + desktop). |

### Phase 6 — Rate limiter (`src/utils/rate-limiter.ts`)

```typescript
class RateLimiter {
  private db: Database;           // SQLite instance
  private maxPerHour: number;     // from config
  private windowMs: number;       // 3_600_000 (1 hour)

  async canAct(actionType: 'react' | 'reply' | 'click'): Promise<boolean>
  async waitIfNeeded(actionType): Promise<void>  // blocks until slot available
  getRemainingSlots(actionType): number
}
```

**How it works:**
- Queries `action_log` for rows within the last hour for the given action type
- If count < `MAX_ACTIONS_PER_HOUR` → allow
- If at limit → calculates time until the oldest action in the window expires, logs it, and optionally sleeps (configurable: block or just skip)
- Default: **skip** (non-blocking) — if over limit, the message is ignored silently

This is the #1 anti-ban measure. Real users don't react 200 times an hour for hours on end.

- System prompt from config (the casual Telegram user persona)

### 4. Human schedule engine (`src/utils/schedule.ts`)

```typescript
class ScheduleEngine {
  private blocks: TimeBlock[];

  getActivityMultiplier(now: Date, timezone: string): number
  // interleaves blocks, returns the multiplier for the current time
  // 0 = fully silent, 0.05 = barely active, 1 = normal, 1.4 = prime time
}
```

**How it works with the dispatch pipeline:**

```
Schedule multiplier = 0.3
    → shouldSkip() probability is multiplied by (1 / multiplier)
    → SKIP_PROBABILITY of 0.35 becomes effectively 0.35 / 0.3 ≈ 1.0 (almost always skip)
    → MAX_ACTIONS_PER_HOUR is scaled: 60 * 0.3 = 18 actions/hour during lunch lull
    → delays stretched: MIN_DELAY * 2, MAX_DELAY * 2 during low-activity blocks
```

At 2am-9am (multiplier 0.05), the bot is effectively dead: ~3 reactions/hour maximum, 95%+ skip rate, 40-300s delays.

### 5. FloodWait handler (`src/utils/flood-wait.ts`)

```typescript
async function withFloodWait<T>(fn: () => Promise<T>, logger: Logger): Promise<T> {
  try {
    return await fn();
  } catch (e) {
    if (e instanceof errors.FloodWaitError) {
      logger.warn({ seconds: e.seconds }, 'FloodWait — sleeping');
      await sleep(e.seconds * 1000);
      return await fn(); // retry once
    }
    throw e;
  }
}
```

Every API call in `actions.ts` wraps in `withFloodWait`. Two-levels: the rate limiter prevents us from hitting FloodWait normally, but this catches edge cases (e.g., Telegram server briefly lowers the threshold).

### 6. Emergency stop (`src/handlers/commands.ts`)

The bot registers an additional event listener on **private chats only**. If `EMERGENCY_STOP_ENABLED=true`:

| Command | Response | Scope |
|---------|----------|-------|
| `/stop` | Disables all outbound actions. Bot still listens but never acts. Persists in DB so it survives restarts. | Sender must match `ADMIN_USERNAME` |
| `/start` | Re-enables actions. | Admin only |
| `/status` | Replies with: uptime, actions today, rate limit %, current schedule multiplier, LLM provider, groups watching | Admin only |
| `/schedule` | Dumps current schedule + multiplier | Admin only |
| `/config` | Lists current keywords, skip probability, action limits (no secrets) | Admin only |

**State persistence:** A `control_state` table in SQLite:
```sql
CREATE TABLE control_state (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
-- "stopped" -> "true" / "false"
```

### 7. Health monitoring (`src/utils/health.ts`)

**Heartbeat:** Every `HEARTBEAT_INTERVAL_MINUTES`, logs `{ uptime, actionsToday, currentRate, groupsOnline }`. If PM2, also writes a heartbeat file that a cron job or external monitor can check.

**Crash loop detection:** On startup, write a timestamp to `logs/last_start.txt`. On crash, PM2 restarts → new startup reads the file. If restarts in last hour > `MAX_RESTARTS_PER_HOUR`, the bot:
1. Logs fatal error
2. Optionally sends a Telegram message to `ADMIN_USERNAME` (if `TELEGRAM_ALERT_ENABLED=true`)
3. Calls `process.exit(1)` with a code that PM2 interprets as "don't restart" (PM2 `max_restarts` + `restart_delay` in ecosystem config)

**Group kick detection:** On `ChatForbidden` or `ChannelPrivate` errors from the target group, remove it from the active group list with a log warning.

### 9. Session encryption

If `SESSION_ENCRYPTION_KEY` is set:
- **On save:** Encrypt session string with AES-256-CBC (random IV, stored alongside ciphertext) using the key
- **On load:** Decrypt with key
- Key derived via PBKDF2 (100k iterations) from the plaintext key so even a weak key gets hardened
- Encrypted files stored in `SESSION_ENCRYPTED_DIR`
- If key is not set, sessions stored as plaintext in `sessions/` (backward compatible)
